## The blocker — no-emit symbol-slot resolution is unreliable

The GOAL kernel dispatcher's first calls resolve function pointers through
the no-emit "data slot" scheme (a writable slot per symbol holding an
`s7`-relative entry offset, patched by the runtime linker). On iOS these
resolve to **empty or garbage values** (call to EE offset 0, SIGSEGV on a raw
EE offset used as a host address, SIGILL on a misaligned computed target),
depending on run-to-run heap/symbol-table state. Evidence chain:

1. Dispatcher crash: `blr` to `0x7000000000` (EE offset 0) — the
   `*listener-function*` value read by the GOAL side was 0 while the C side
   (same name, `intern_from_c`) held `s7.offset`; the two sides resolved
   **different symbol-table entries** (`goal-side entry=0x1982cc` vs
   `cside entry=0x198cb4`).
2. Top-level crash: SIGSEGV loading from a raw EE offset (`0x1c4b68`) as a
   host address — the ADRP/ADD slot pair was patched with an EE-relative
   target that the code uses as a host address.
3. Host (non-deterministic, 1/3 of runs at one point; 4/4 in a later clean
   rerun): same class of fault during the gkernel top-level (SIGILL/SIGSEGV
   at computed targets).

Root-cause characterization: `find_symbol_from_c`/`intern_from_c` use a
linear-probe-with-early-stop hash scheme that is **order-dependent** — a
symbol interned early can become unfindable after more interning, so the
kernel link's intern (many symbols) and the C-side's later intern of the same
name can create **two entries for one name**, and the GOAL-side reads the
entry the C side never wrote. This is a defect in the H3 no-emit work's
interaction with OpenGOAL's symbol table, not an ARM64 encoding problem (the
S1.1 harness proves every emitted word is a valid instruction).

## Fixes attempted (all documented in `docs/00-loop-log.md`)

1. `ListenerFunction->value = 0` under OTTSEL_IOS (C-side) — no effect on the
   GOAL-side read (different entries).
2. Direct patch of the GOAL-side slot entry to the `nothing` function (via
   the dispatcher's slot chain) — made the listener call a no-op, but the
   dispatcher then faults on the *next* garbage-resolved call.
3. Reordered `InitHeapAndSymbol` under OTTSEL_IOS to register C exports
   (InitListener/InitMachineScheme) *before* the kernel link — the linker's
   probe still missed the pre-created entries (order-dependence).
4. Gated signal handler (SIGSEGV/SIGBUS/SIGILL -> explicit log + clean
   exit) — the S1.3 "explicit gated error, no crash loop" fallback; works.

## Options for the next agent

- **A. Fix the symbol-table order-dependence** (highest value, moderate
  scope): make `find_symbol_from_c`/`intern_from_c` robust to late interning
  (e.g., rehash or full-table scan on miss, or intern every C-export name
  *before* the kernel link and force the linker to reuse it). Would fix the
  whole class; needs care to not change the host's working behavior.
- **B. Replace the no-emit data-slot scheme with an offline prelink** (the
  H2.5 generated-native direction): resolve all symbol/function slots in the
  object at build time instead of at link time. Larger change, aligns with
  the packaging decision in doc 10.
- **C. Make the iOS dispatcher tolerate garbage function pointers** (hacky,
  not recommended): patch every slot the kernel calls; whack-a-mole.

## Recommendation

Option A, done host-first and verified against the H3 host boot (which must
remain 100% reliable — it currently shows a rare non-deterministic crash of
the same class), then re-verified on iOS. The S1.1 harness + the gated
handler keep this safe to iterate: invalid encodings are caught at compile
time and runtime faults stop with a clear message instead of crash-looping.
