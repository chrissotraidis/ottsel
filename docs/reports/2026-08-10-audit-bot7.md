## Mandatory claims

1. **Fault shape — PASS.** `s21-trace4-boot.log` ends `signal 11 at
   pc=0x1f2df4 fault addr=0x1f2df4`; its handler reads
   `run-function-in-process` value `0x001f2df4`. Live LLDB reports
   `ee + 0x1f2df4 = 0x70001f2df4` in an `r-x` region.
2. **Call chain — PASS.** Trace4 records pp `0x24783b` throughout and ends
   `gstate 0x550514 -> set-to-run 0x1f3454/0x1f1d14 -> throw-dispatch
   0x001f1bf4`. The raw rfn value occurs in the return path, while recorded
   caller LRs are absolute.
3. **Offline reproduction — PASS.** Re-ran
   `out/jak-project/build/h1/game/ottsel-cgolink-dump out/jak-project/out/jak1/iso`.
   It found `throw-dispatch pattern found @ 0x001b1bf4`, matching Simulator
   `0x001f1bf4` under the documented kernel offset delta.
4. **throw-dispatch — PASS.** Live disassembly at `ee+0x1f1bf4` agrees with
   `gkernel.gc:1531`: it adds x22 to the stored 32-bit `ra` before `ret`.
   With x22 `0x7000000000`, that return is absolute and cannot be raw
   `0x001f2df4`.
5. **catch-frame-new contract — CONTRADICT (corrected).** The contract and
   observed rfn catch-frame `ra=0x0244a6c0` are real, but the conclusion that
   this cannot explain the fault is false. Live code at `ee+0x0244a63c` calls
   rfn; the resulting catch returns to `0x0244a6c0`, bypassing rfn's intended
   post-call continuation `0x001f2fdc`. The trampoline then reaches
   `ee+0x0244a6f8` (`ldr x30, [sp], #16`) and its `ret` at
   `ee+0x0244a700`, which consumes stack slot `0x7007fffe80 = 0x001f2df4`.
6. **Shim hypothesis — CONTRADICT (now proven).** A focused A1.0 regression
   was added for the stack value of a GOAL->GOAL call. It failed on the old
   emitter (no post-BLR continuation slot/restoration pair), then passed after
   the minimal fix: preserve incoming x30, push `adr x17, post-blr`, and pop
   the continuation before restoring incoming x30. This is a semantic proof;
   the S2.1 boot proof remains pending.
7. **Git hygiene — PASS with scope note.** `8bab4a8` and `60241e1` have the
   stated scope; the canonical patch was unchanged by them and applies cleanly
   to a fresh pin worktree. It intentionally does not reverse-apply to the
   live upstream worktree because later S2.1 source changes are not yet folded
   into the canonical patch; regeneration is required before the next gate
   checkpoint.
